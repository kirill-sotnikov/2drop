# 2drop

Передача одного или нескольких файлов между браузерами после согласия получателя. QR и ID открывают
страницу отправки; исходные байты идут через надёжный упорядоченный WebRTC DataChannel.
Получатель скачивает один исходный файл или один ZIP без сжатия.

## Запуск

Нужны Node.js 24+ и Yarn 4 (версия закреплена в `packageManager`).

```sh
yarn install
cp .env.example .env
cp web/.env.local.example web/.env.local
yarn dev
```

Откройте <http://localhost:8081>. Команда запускает Next.js и signaling вместе;
завершение любого процесса останавливает второй. Для локального испытания используйте
два разных браузера или обычное и приватное окна. В одном окне откройте «Получить»,
в другом введите ID, выберите один или несколько файлов и предложите передачу. Получатель видит весь список и общий размер, затем нажимает «Принять».

`GET http://localhost:3001/health` возвращает `200` и `{"status":"ok"}`.
WebSocket расположен по `/ws`; метрики Prometheus доступны по `GET /metrics`.
Остальные HTTP-маршруты signaling возвращают `404`.

## Пакеты и проверки

| Workspace  | Назначение                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------- |
| `web`      | Next.js App Router, React, TypeScript, vanilla-extract, QR (`qrcode`), ZIP STORE (`fflate`) |
| `service`  | Отдельный Node.js-процесс, `node:http`, `ws`, `node:crypto`                                 |
| `protocol` | Общие Zod-схемы и типы сообщений с версией протокола                                        |

```sh
yarn typecheck
yarn lint
yarn test
yarn build
yarn test:e2e
```

`yarn test` проверяет сервер через настоящие WebSocket-соединения и файловый канал
отдельно от браузера: согласие, роли, восстановление и коллизии ID, таймауты,
конкуренцию, отмену, ограничения, порядок сообщений и целостность байтов.

`yarn test:e2e` после `yarn build` запускает собранный signaling на `3101`, Next.js
в режиме разработки на `3100` и два независимых контекста Chrome. Проверяет сохранение
ID при навигации и перезагрузке, QR, передачу бинарного/пустого файла, SHA-256 скачанного
файла, отказ, отмену и повтор. Также проверяет семь файлов в одном ZIP, включая пустые
файлы, Unicode и совпадающие имена, отсутствие неполного архива при отмене и общий лимит. Дополнительно передаёт текст, PNG, ZIP и файл ровно
100 000 000 байт; проверяет отказ для 100 000 001 байта. Режим разработки также проверяет React Strict Mode.
На macOS используется установленный Google Chrome. На других системах выполните
`yarn playwright install chromium` или укажите путь в `PLAYWRIGHT_CHROMIUM_EXECUTABLE`.
Тесты используют локальную прямую передачу без внешних ICE-сервисов.

`yarn check` объединяет типы, ESLint, модульные/серверные тесты и сборку.
Форматирование: `yarn prettier --write <изменённые-файлы>`.

## Конфигурация

Сервер читает корневой `.env`. Next.js читает `web/.env.local`; переменные
`NEXT_PUBLIC_*` фиксируются в клиентской сборке. После их изменения пересоберите `web`.
Секрет TURN хранится только на сервере и coturn, без префикса `NEXT_PUBLIC_`.

| Переменная сервера        | По умолчанию                                          |
| ------------------------- | ----------------------------------------------------- |
| `HOST`, `PORT`            | `0.0.0.0`, `3001`                                     |
| `ALLOWED_ORIGINS`         | `http://localhost:8081,http://127.0.0.1:8081`         |
| `MAX_FILE_BYTES`          | `100000000` (общий размер исходных файлов в передаче) |
| `RECONNECT_MS`            | `120000`                                              |
| `OFFER_TIMEOUT_MS`        | `60000`                                               |
| `TRANSFER_TIMEOUT_MS`     | `1800000`                                             |
| `HEARTBEAT_MS`            | `15000`                                               |
| `MAX_CONNECTIONS`         | `2000`                                                |
| `MAX_CONNECTIONS_PER_IP`  | `20`                                                  |
| `MAX_SESSIONS`            | `4000`, включая окно восстановления                   |
| `LOG_LEVEL`               | `info`; уровни Pino, включая `debug` и `silent`       |
| `NODE_ENV`, `APP_VERSION` | `development`, `unknown`; окружение и релиз в логах   |
| `METRICS_TOKEN`           | Пусто; при настройке `/metrics` требует bearer-токен  |
| `ICE_SERVERS_JSON`        | `[]`, массив объектов `RTCIceServer`                  |
| `TURN_URLS`               | Пусто; список URL через запятую                       |
| `TURN_SECRET`             | Пусто; общий секрет coturn                            |
| `TURN_TTL_SECONDS`        | `3600`, дольше максимальной передачи                  |

`NEXT_PUBLIC_SIGNALING_URL` задаёт `ws://…/ws` локально и `wss://…/ws` в production.
Если он не задан, HTTP-прототип использует текущий hostname и порт `3001`; на HTTPS
клиент требует явно настроенный WSS-адрес. `NEXT_PUBLIC_ICE_TRANSPORT_POLICY=relay`
включает принудительный TURN, `all` — обычный выбор маршрута.

Сервер ограничивает поиск ID (60/мин), предложения (20/мин), создание соединений
(60/мин) и сообщения (600/мин) по адресу TCP-соединения. Не доверяет `X-Forwarded-For`.
За reverse proxy адрес общий: настройте лимиты под ожидаемое число пользователей;
ограничения по исходному IP следует дополнительно настроить на proxy.

## Логи и метрики

Signaling пишет JSON-логи через Pino в stdout. События имеют постоянное имя `event`,
уникальный `eventId` и идентификаторы соединения, внутренней сессии и передачи.
Секреты, публичные коды получения, имена файлов и SDP/ICE в логи не записываются.

`GET /metrics` отдаёт метрики подключений, сессий, сообщений, ошибок и передач,
а также стандартные метрики процесса Node.js. Для production задайте `METRICS_TOKEN`
и оставьте маршрут доступным только сборщику внутри сети; публичный router Traefik
для signaling должен пропускать только `/ws` и `/health`.

Формат событий, список метрик, настройка сбора и примеры запросов описаны в
[`deploy/observability.md`](deploy/observability.md).

## HTTPS, STUN и TURN

Публичный запуск требует домена, HTTPS/WSS и работающего TURN. Конфигурации в `deploy/`
являются шаблонами, а не развёрнутой инфраструктурой.

1. Установите coturn на публичном сервере, заполните `deploy/turnserver.conf.example`
   реальными адресами, доменом, сертификатом и случайным общим секретом.
2. Откройте `3478/UDP`, `3478/TCP`, `5349/TCP` и relay-диапазон `49160–49260/UDP`.
   Для сетей, допускающих только TLS на `443`, нужен отдельный TURN-адрес/хост с
   `tls-listening-port=443` и соответствующим `turns:` URL. Caddy HTTP-proxy не заменяет TURN.
3. Настройте сервер, например:

   ```dotenv
   ALLOWED_ORIGINS=https://drop.example.com
   ICE_SERVERS_JSON=[{"urls":"stun:turn.example.com:3478"}]
   TURN_URLS=turn:turn.example.com:3478?transport=udp,turn:turn.example.com:3478?transport=tcp,turns:turn.example.com:5349?transport=tcp
   TURN_SECRET=ТОТ_ЖЕ_СЛУЧАЙНЫЙ_СЕКРЕТ
   ```

4. В `web/.env.local` задайте `NEXT_PUBLIC_SIGNALING_URL=wss://drop.example.com/ws`.
   Настройте Caddy по `deploy/Caddyfile.example`, выполните `yarn build`, затем
   `yarn start`. Для постоянно работающего сервиса используйте менеджер процессов.
5. Проверьте передачу с `all`, затем пересоберите с `relay` и проверьте снова.
   Подтвердите выбранную пару кандидатов через браузерные WebRTC-диагностики.

Временные TURN-учётные данные выдаются по WebSocket и обновляются при принятии
каждой передачи. Файлы не проходят через signaling. TURN ретранслирует зашифрованный
WebRTC-трафик, расходуя серверную пропускную способность.

## Поведение и ограничения

- Сессии и передачи хранятся в памяти одного signaling-процесса; перезапуск инвалидирует ID.
- Публичный ID содержит 8 случайных символов. Секрет восстановления хранится в
  `sessionStorage`, не попадает в QR и публичные сообщения. После отключения ID можно
  восстановить в течение 2 минут. Дублированная вкладка получает независимый ID,
  если исходная сессия всё ещё занята.
- Получатель принимает всю подборку одним действием; участник не может одновременно вести другую передачу.
  До 100 файлов и суммарно до `MAX_FILE_BYTES` исходных байтов; размер списка метаданных также ограничен.
  При обновлении ID ожидающие предложения отменяются. Во время передачи обновление запрещено.
- SDP/ICE пересылаются только после согласия и только между участниками конкретной передачи.
- Отправитель читает файл частями до 16 КиБ, учитывает `maxMessageSize`, приостанавливает
  чтение при очереди более 1 МиБ и продолжает при 256 КиБ. Base64 и сжатие не используются.
- При обрыве signaling/WebRTC и после 30 секунд без прогресса файл нужно передать заново.
  Восстановление ID не возобновляет байты. После полного приёма получатель подтверждает результат.
- Для нескольких файлов получатель постепенно собирает ZIP STORE; один файл сохраняется в исходном формате.
  Архив финализируется и становится доступен только после приёма всей подборки.
  Совпадающие имена получают суффиксы, пути и недопустимые символы в именах ZIP нейтрализуются.
- Данные полученного файла/архива остаются в браузере. Blob URL живёт до принятия следующей
  передачи или ухода из приложения; клик по скачиванию его не отзывает. Служебные данные ZIP
  немного увеличивают объём сверх суммы исходных файлов.
- Имя и MIME считаются непроверенными данными; приложение не исполняет и не встраивает файл.
- Постоянное файловое хранилище, аккаунты, папки, сжатие и возобновление не реализованы.
- Фоновая передача и работа при блокировке экрана не гарантированы.

Лимит 100 МБ не является заявлением о поддержке всех устройств. Перед публичным запуском
нужны проверки Safari/iOS, Android, Firefox, разных сетей, TURN и памяти у верхнего лимита.
Клиент и сервер используют версию протокола 2 и должны обновляться совместно.
Незавершённые проверки перечислены в `plan.md`; результаты записываются в `verification.md`.
